# Архитектура

## Обзор

```
┌──────────────── Telegram-клиент ────────────────┐
│  Mini App (React SPA)          Чат с ботом      │
└───────┬─────────────────────────────▲───────────┘
        │ HTTPS /api/v1               │ Bot API: sendMessage,
        │ (JSON, Bearer-токен)        │ getUpdates (long polling)
┌───────▼─────────────────────────────┴───────────┐
│  backend (Go, один бинарник, одна реплика)       │
│   ├─ HTTP API                                    │
│   ├─ reminders: планировщик + отправка           │
│   └─ bot poller: /start и кнопки в сообщениях    │
└───────┬─────────────────────────────────────────┘
        │ pgx
┌───────▼───────┐
│ PostgreSQL 18 │
└───────────────┘
```

Пока пользователей мало и нагрузка небольшая, все компоненты работают в одном процессе. Если понадобится, напоминания и бота можно вынести в отдельные сервисы, модель данных при этом не меняется.

После MVP веб-версия использует тот же фронтенд и тот же API. Меняются только способ входа и адаптер платформы.

## Выбор БД: PostgreSQL (согласовано)

- **Реляционная модель.** Дела ↔ категории (многие-ко-многим), дерево категорий, серии → экземпляры, привычки → отметки, партнёры и доступы. Внешние ключи защищают целостность.
- **Интервалы времени.** `tstzrange` и `tstzmultirange` вместе с `range_agg` и `unnest` позволяют посчитать в SQL:
  - общее занятое время без двойного учёта параллельных дел;
  - позже — общее свободное время нескольких людей: окно − (занятость A ∪ B ∪ …).
- **Деревья и статистика.** Рекурсивные CTE для дерева категорий, `generate_series` по локальным дням, оконные функции.
- **Очередь напоминаний** на `SELECT … FOR UPDATE SKIP LOCKED` — без Redis и брокеров.
- **`uuidv7()`** встроена в PostgreSQL 18.
- **Экосистема Go:** pgx, sqlc, goose.

У нас будет **свой** контейнер Postgres в нашем `docker compose`, отдельно от Postgres проекта `diary`.

## Модель данных

Всё время хранится в `timestamptz`. Идентификаторы — `uuid` (`uuidv7()`).

### Пользователи и вход

**users**

- `id`, `display_name`, `timezone` (IANA)
- `slot_minutes` (5, 10, 15, 30 или 60), `default_view` (`day` | `three_days` | `week`), `deviation_threshold_minutes`
- `created_at`

**user_identities** — способы входа:

- `user_id`, `provider`, `provider_user_id`
- `provider` — `telegram` (Mini App и Login Widget — один провайдер); `email` добавится позже, только как второй способ входа к существующему аккаунту
- для Telegram: `username`, `first_name`, `last_name`, `photo_url`, `language_code`
- для email: `password_hash` (argon2id), `email_verified_at`
- `UNIQUE(provider, provider_user_id)`

У одного пользователя может быть несколько способов входа (FR-10.4).

**sessions**

- `id`, `user_id`, `token_hash` (sha256), `created_at`, `expires_at`, `last_used_at`

### Категории

**categories**

- `id`, `user_id`, `parent_id` (NULL — верхний уровень), `name`, `color` (hex), `archived_at`, `created_at`
- Защита от циклов при переносе — в сервисе: нельзя сделать родителем категорию из своего же поддерева. Структурные изменения одного пользователя сериализуются advisory-блокировкой.
- Родитель всегда принадлежит тому же пользователю: составной внешний ключ `(parent_id, user_id)`.
- Удаление каскадное: удаляется всё поддерево, а категории снимаются с дел (дела остаются).
- Архивация действует на всё поддерево. Активную категорию нельзя создать или перенести под архивную. Возврат из архива действует на одну категорию, подкатегории остаются архивными; пока родитель в архиве, вернуть потомка нельзя.
- Название — 1–100 символов без пробелов по краям, цвет — `#rrggbb` в нижнем регистре. Уникальность названий не требуется.
- «Категория + все предки» считается рекурсивным CTE. Используется в статистике и при наследовании напоминаний.

### Дела

- **Разовое дело** — одна строка в `task_instances`, без серии.
- **Регулярное дело** — шаблон в `task_series` и материализованные экземпляры в `task_instances`.

**task_series** — шаблон регулярного дела:

- `id`, `user_id`, `title`, `description`
- `rrule` (RRULE без DTSTART), `dtstart_local` (`timestamp` без зоны), `timezone` (пояс пользователя на момент создания серии), `duration_minutes`
- `habit_id` — NULL, если серия не привязана к привычке (этап 7); при разделении серии («это и следующие») копируется в новую
- `created_at`, `updated_at`

**series_categories** — `(series_id, category_id)`.

**task_instances** — конкретное дело в календаре:

- `id`, `user_id`, `series_id` (NULL у разовых), `original_start` (начало по правилу — ключ экземпляра внутри серии)
- `title`, `description`
- `planned_start`, `planned_end` — оба NULL у дел вне плана
- `actual_start`, `actual_end` — `actual_end` NULL, пока идёт таймер
- `status`: `planned` | `in_progress` | `done` | `partial` | `not_done` | `rescheduled` | `cancelled`
- `rescheduled_from_id` — ссылка на исходное дело при переносе; уникальный индекс, у дела не больше одного «продолжения»
- `comment` — причина отклонения или переноса
- `is_detached` — экземпляр изменён отдельно, правки «все» его не трогают
- `created_at`, `updated_at`

Ограничения и индексы:

- `UNIQUE(series_id, original_start)`;
- CHECK: план задан целиком или отсутствует целиком; `planned_end > planned_start`; `actual_end >= actual_start`; у дела вне плана есть `actual_start`;
- индексы `(user_id, planned_start)` и `(user_id, actual_start)`.

**instance_categories** — `(instance_id, category_id, user_id)`; составные внешние ключи не дают связать дело и категорию разных пользователей. Экземпляр хранит **свою** копию полей и категорий: правка «только это» не требует особых случаев, а статистика соединяет таблицы напрямую.

Ограничения полей: название дела — 1–200 символов, описание — до 5000. Окно `GET /instances` — не более 100 дней. Таблица `task_instances` создаётся миграцией этапа 3 только с полями плана; серия, факт, ссылка переноса и дела вне плана добавляются миграциями этапов 4–5.

Отклонения **не хранятся**. Они вычисляются из плана, факта и `deviation_threshold_minutes`.

### Привычки

**habits**

- `id`, `user_id`, `title`, `kind` (`boolean` | `quantity`), `target_value`, `unit` (для количественной; для «да/нет» цель 1)
- `frequency` (`daily` | `weekdays` | `times_per_week`), `weekdays` (ISO 1–7, понедельник = 1), `times_per_week`
- `color`, `archived_at`, `created_at`

Привычка в сетке дня — это `task_series` с заполненным `habit_id`. Положение в сетке (время суток и длительность) отдельно в `habits` не хранится: оно читается из серии, поэтому серия, удалённая из календаря, не оставляет висящих полей. Изменение частоты или времени привычки заменяет серию: запланированные экземпляры пересоздаются, отмеченные остаются историей.

**habit_logs**

- `habit_id`, `date` (локальная дата), `value` (1 для «да/нет», накопленная сумма для количественной)
- `base_value` — значение, которое было у дня вручную до того, как его засчитал экземпляр; при снятии отметки возвращается, а не удаляется.
- `task_instance_id` — экземпляр из сетки, который засчитал этот день; NULL для ручной отметки. Нужен, чтобы снятие отметки экземпляра убирало засчитанное им значение, но не трогало поправленное вручную. При удалении экземпляра значение остаётся (ссылка обнуляется).
- `UNIQUE(habit_id, date)`; значение 0 не хранится: строка удаляется

### Напоминания

Настройки лежат в отдельных таблицах. Каждая строка `reminder_settings` — это «у этого уровня свои настройки». Если строки нет, уровень наследует настройки от более общего.

**reminder_settings**

- `id`, `user_id`
- `scope`: `global` | `category` | `series` | `instance` | `habit`
- `category_id` | `series_id` | `instance_id` | `habit_id` — ровно одно, по `scope`; у каждого свой внешний ключ с `ON DELETE CASCADE`, поэтому настройки уходят вместе с категорией, серией, делом или привычкой
- `enabled` — `false` значит «без напоминаний на этом уровне»; у строки `global` это общий выключатель
- `quiet_start`, `quiet_end` — минуты от локальной полуночи; только у строки `global`; интервал может переходить через полночь
- Уникальность — частичные индексы по каждому уровню
- Строка `global` с правилами по умолчанию (за 10 минут до начала и запрос отметки сразу после конца) создаётся триггером БД при создании пользователя; миграция создала её существующим.

**reminder_rules**

- `id`, `setting_id`
- `kind`: `before_start` | `after_end` | `not_started` | `overrun` | `habit_time`
- `offset_minutes` (0…10080) — для первых четырёх типов; `before_start` — до начала, `not_started` — от начала, `after_end` и `overrun` — от конца
- `time_of_day` — минуты от полуночи, для `habit_time`
- Не больше 20 правил на уровень, одинаковые правила хранятся один раз

**Как определяются действующие правила для экземпляра.** Берётся первый уровень, у которого есть своя строка:

1. `instance`;
2. `series`, если экземпляр из серии;
3. категории дела. Для каждой категории берутся её собственные настройки или настройки ближайшего предка, у которого они есть. Правила всех найденных категорий объединяются без дублей. Если ни у одной категории и ни у одного предка своих настроек нет, уровень пропускается;
4. `global`.

Напоминания отправляются, только если у `global` `enabled = true`. Для привычек используются правила `scope = habit` с `kind = habit_time`.

**notifications** — очередь отправки (outbox):

- `id`, `user_id`, `instance_id` или `habit_id`, `kind`
- `dedupe_key` (UNIQUE), например `inst:<id>:before_start:10` или `habit:<id>:2026-10-05:21:00`
- `send_at`, `sent_at`, `gave_up_at`, `attempts`, `last_error`, `telegram_message_id`
- Ключ `inst:<id>:<kind>:<offset>:<planned_start unix>` содержит плановое начало: перенос дела даёт новые напоминания.

### Совместное планирование (после MVP, набросок)

- **partner_invites** — `token`, `inviter_id`, `expires_at`, `accepted_by`, `accepted_at`.
- **partnerships** — пара пользователей, взаимная связь; создаётся, когда приглашение принято.
- **task_access_grants** — `owner_id`, `grantee_id`. Односторонний доступ к названиям дел владельца.
- Поле `visibility` у `task_series` и `task_instances`: `partners` | `granted` | `private`. Приватность по умолчанию хранится в настройках пользователя.
- Что видит партнёр:
  - `private` → «занят»;
  - `granted` → название, если есть grant, иначе «занят»;
  - `partners` → название.
- Общее свободное время: окно − объединение занятости выбранных людей, считается на `tstzmultirange`.
- Приглашение в Telegram можно сделать ссылкой `t.me/<бот>?startapp=<token>`: Mini App получит токен в `start_param`.

## Ключевые потоки

### Вход (Telegram Mini App)

1. Фронтенд берёт сырой `initData` из `Telegram.WebApp` и отправляет `POST /api/v1/auth/telegram { initData, timezone }`.
2. Бэкенд проверяет подпись: `secret = HMAC_SHA256("WebAppData", bot_token)`, хэш полей должен совпасть. Также проверяется свежесть `auth_date`.
3. Бэкенд создаёт или обновляет `users` и `user_identities`, создаёт строку `global` в настройках напоминаний и выдаёт случайный сессионный токен. В БД хранится только хэш токена.
4. Фронтенд держит токен в памяти и шлёт `Authorization: Bearer …`. На 401 повторно входит по текущему `initData`.

Параметры:

- `initData` считается свежим, если `auth_date` не старше 24 часов (`INITDATA_MAX_AGE`); допускается расхождение часов до минуты.
- Сессия живёт 30 дней (`SESSION_TTL`); просроченные сессии удаляются при очередном входе.
- Часовой пояс устройства используется только при создании аккаунта; дальше его меняют в настройках.
- Значения настроек по умолчанию: слот 30 минут, вид «день», порог отклонения 10 минут.
- Все маршруты, кроме `/healthz`, `/auth/config`, `/auth/telegram`, `/auth/telegram-widget` и `/auth/dev`, требуют сессию. Список открытых маршрутов — `publicPaths` в `backend/internal/httpapi/auth.go`, он должен совпадать с операциями `security: []` в `openapi.yaml`.
- Фронтенд при ответе 401 один раз входит заново и повторяет запрос.

В режиме разработки (`APP_ENV=dev`, `DEV_AUTH=true`) можно войти без Telegram через `POST /auth/dev`: так приложение открывается в обычном браузере, и на нём можно гонять e2e-тесты. Это отдельный провайдер `dev` в `user_identities`; параметр `key` позволяет завести несколько тестовых пользователей. Сервер не запустится, если `DEV_AUTH=true` при `APP_ENV` не `dev`.

### Вход (веб-версия)

Сайт тот же, что у Mini App (`https://plan.…`), и фронтенд тот же: вне Telegram работает адаптер `browser`.

1. При запуске фронтенд запрашивает `GET /me`. Сессия веб-версии — в cookie, поэтому, если пользователь уже входил, этого достаточно.
2. На 401 фронтенд пробует `POST /auth/dev`. В проде он отвечает 404, и показывается страница входа.
3. Страница входа берёт `telegram_bot_id` из `GET /auth/config` (это числовая часть токена бота). По кнопке вкладка уходит на страницу входа Telegram: `https://oauth.telegram.org/auth?bot_id=…&origin=…&request_access=write&return_to=<текущая страница>`. Сторонний скрипт `telegram-widget.js` не используется (его режут блокировщики рекламы), всплывающего окна тоже нет (его блокируют браузеры). Код — в `src/platform/telegram.ts`.
4. Telegram возвращает на `return_to` с подписанными полями в `#tgAuthResult=<base64url JSON>`. Фронтенд убирает их из адреса и отправляет строками и без изменений: `POST /auth/telegram-widget { auth_data, timezone }`.
5. Бэкенд проверяет подпись. Строка для проверки собирается как у `initData`, но ключ другой: `secret = SHA256(bot_token)`. Свежесть `auth_date` проверяется по тому же `INITDATA_MAX_AGE`. Пользователь — тот же `provider = telegram`, `provider_user_id` = id в Telegram, то есть тот же аккаунт, что в Mini App. Виджет не сообщает язык, поэтому сохранённый `language_code` остаётся.
6. Сессия уходит в cookie `session` (`HttpOnly`, `Secure` вне dev, `SameSite=Lax`, `Path=/api/v1`), токена в теле ответа нет.
7. `POST /auth/logout` удаляет сессию и стирает cookie. Кнопка «Выйти» есть только в браузере.

Безопасность:

- Middleware принимает `Authorization: Bearer …` (Mini App, dev) или cookie `session`. Bearer важнее.
- **CSRF.** Браузер прикладывает cookie и к запросам с чужих сайтов, поэтому запросы с cookie, а также `POST /auth/telegram-widget`, проходят через `http.CrossOriginProtection` (`Sec-Fetch-Site`, иначе `Origin` против `Host`). Небезопасный метод с другого источника получает 403. Соседний поддомен (`diary`) — тоже другой источник.
- Для окна входа в BotFather должен быть указан домен сайта (`/setdomain`), иначе Telegram отвечает «Bot domain invalid».
- Без токена бота вход через виджет отклоняется: подпись с пустым ключом подделает кто угодно.

### Повторы и материализация

- **Правило.** Поддерживается подмножество RRULE, которое умеет редактор (FR-4.1): `FREQ` = `DAILY`/`WEEKLY`/`MONTHLY`/`YEARLY`, `INTERVAL`, `BYDAY` (список дней для `WEEKLY`; один порядковый день вроде `2TU` или `-1FR` для `MONTHLY`), `BYMONTHDAY` (`MONTHLY`), `COUNT` или `UNTIL` (UTC). Всё остальное сервер отклоняет. Форму повтора ↔ RRULE собирает фронтенд.
- **Развёртка в «плавном» времени.** Правило разворачивается по стенным часам пояса серии (`rrule-go` получает время без зоны), а затем каждое вхождение переводится в момент по правилам RFC 5545: несуществующее время (часы идут вперёд) берётся со смещением до перехода, повторяющееся (часы идут назад) — первое вхождение. Сама `rrule-go` при переходе на летнее время ошибается на час, поэтому зону ей не отдаём.
- **Ленивая материализация без горизонта.** Серия — это правило, а не копии вперёд. `GET /instances?from&to` перед ответом разворачивает правила всех серий пользователя в этом окне (с запасом на длительность) и вставляет недостающие экземпляры через `ON CONFLICT (series_id, original_start) DO NOTHING`, под advisory-блокировкой пользователя. Любое окно (хоть через год, хоть в прошлом) работает одинаково, промежуток между окнами не генерируется. Поле `generated_until` не нужно. Статистика (этап 6) и планировщик напоминаний (этап 8) вызывают ту же функцию `Materialize` для своих интервалов.
- **Предохранители.** Окно запроса — не больше 100 дней; одна развёртка — не больше 1000 вхождений.
- Удаление одного экземпляра — это `status = cancelled`. Строка остаётся, поэтому при повторной генерации экземпляр не появится снова; в `GET /instances` отменённые не попадают.
- **«Только это»:** правится экземпляр, ставится `is_detached = true`.
- **«Все»:** меняется шаблон (название, описание, категории, время суток, длительность, правило); экземпляры серии со статусом `planned` и без `is_detached` удаляются и создаются заново при следующем запросе их окна. Поэтому **id таких экземпляров после правки серии меняются**. Отделённые, отмеченные и отменённые не трогаются.
- **«Это и следующие»:** серия делится на две:
  - у старой `UNTIL` ставится на секунду раньше этого экземпляра (при `COUNT` — число вхождений до него);
  - новая серия начинается с этого экземпляра, с новым шаблоном; при `COUNT` общее число вхождений сохраняется, при `UNTIL` дата окончания та же;
  - перезаписываемые экземпляры старой серии начиная с этой точки удаляются;
  - если до этого экземпляра вхождений нет, это то же, что «Все».
- **Дата при правке серии.** Правка времени у «Все» и «Следующих» меняет только время суток и длительность. Перенос на другую дату — это правка одного экземпляра; сервер отвечает `series_date_change`.
- **Удаление.** «Все» и «Следующие» удаляют экземпляры со статусом `planned`, включая отделённые; отмеченные остаются разовыми делами (`series_id` сбрасывается).
- **Ключ экземпляра** — его исходное время (`original_start`). Чтобы удалённые, изменённые отдельно и отмеченные экземпляры не «воскресали» и не дублировались, они сопровождают правки серии:
  - при «Это и следующие» оставшийся хвост (отменённые, отделённые, отмеченные экземпляры от точки разреза) переходит в новую серию;
  - при смене времени суток (в «Все» и «Следующих») ключи таких экземпляров пересчитываются на новое время суток в тот же локальный день. У серии не больше одного вхождения в день, поэтому день однозначно определяет слот.
- **Блокировки.** Правки и удаления серий берут эксклюзивный advisory-lock пользователя, материализация — общий: окна разворачиваются параллельно друг с другом, но не во время правки серии.
- Удалить отдельный отмеченный экземпляр серии можно (клиент предупреждает, что факт пропадёт): строка становится `cancelled` без факта и не создаётся заново. Отменённые экземпляры уходят вместе с серией или её хвостом.
- **Инвариант:** экземпляр с фактом или со статусом, отличным от `planned`, никогда не меняется при правке серии. Условие «можно переписывать» записано в одном запросе (`DeleteSeriesInstances`); на этапе 5 к нему добавится «без факта».

### Отслеживание и перенос

Состояния и факт согласованы проверками таблицы `task_instances`:

| Статус | План | Факт |
|---|---|---|
| `planned` | обязателен | нет |
| `in_progress` | любой | начало есть, конца нет |
| `done`, `partial` | любой | начало и конец |
| `not_done`, `rescheduled`, `cancelled` | любой | не проверяется (у «не выполнено» факта нет) |

Дело вне плана — строка без `planned_start`/`planned_end`; у неё всегда есть `actual_start`.

- **«Выполнено»:** `actual = planned`, `status = done`. Из `planned`, `not_done`, `in_progress`; у уже `done`/`partial` ничего не меняется (повторное нажатие не затирает отредактированный факт); для дела вне плана и для перенесённого — `invalid_state`.
- **«Старт»:** `actual_start = now`, `status = in_progress`. Только из `planned` и `not_done`; повторный старт — `invalid_state`. Строка блокируется (`FOR UPDATE`), поэтому два одновременных «Старта» дают один запуск.
- **«Стоп»:** `actual_end = now`, `status = done`; если часы отстают и `now` не позже начала, конец — начало плюс секунда (факт нулевой длины не бывает). Потом статус можно сменить на `partial`.
- **Ручная правка** (`PATCH …/tracking`): статус, начало и конец факта, комментарий. Статус `planned` и `not_done` стирают факт. Без статуса его определяет факт: только начало — `in_progress`, начало и конец — `done` (у `partial` остаётся `partial`). `done`/`partial` без времени берут план. Перенесённое дело не меняется (см. ниже). Факт не может быть в будущем (`fact_in_future`, допуск минута) — это относится к введённым вручную временам и к делам вне плана, но не к «Выполнено», которое берёт план как есть.
- **«Снять отметку»** — это `status = planned`. Для серии дело снова становится перезаписываемым (см. «Повторы и материализация»).
- **Перенос:** в одной транзакции исходному делу ставится `status = rescheduled` и комментарий-причина; создаётся новое разовое дело (`series_id = NULL`) с копией названия, описания и категорий и `rescheduled_from_id` = исходное. Перенести можно дело из `planned` или `not_done`. У дела не больше одного «продолжения» (уникальный индекс). Исходное остаётся в календаре, слот серии за ним сохраняется. Перенесённое дело — история: ни обычная правка, ни отслеживание его не меняют. Если новое дело удалить, перенос теряет смысл: у исходного пропадает ссылка вперёд, и тогда отметку можно снять (дело вернётся в «запланировано» и его можно перенести снова). Если исходное разовое удалить — у нового пропадает ссылка назад.
- **Удаление отмеченного дела** допустимо: разовое удаляется целиком, экземпляр серии становится `cancelled` без факта.
- **Отклонения** считает функция `task.Deviations` (план, факт, порог пользователя); ответ API содержит их списком. Для `done`/`partial` сравниваются начало, конец и длительность, для `in_progress` — только начало. Разница считается отклонением от порога включительно (при пороге 0 — любая разница в минуту).
- **Окно запроса** `GET /instances` находит дело по плану или по факту (идущий таймер длится до «сейчас»). Ответ строится из представления `instance_details` (категории и ссылки переноса в обе стороны).
- **Неотмеченные** (FR-5.9) определяет клиент: `status = planned` и конец плана в прошлом.
- Напоминания исходного дела при переносе (этап 8) удаляются.

### Статистика

Агрегаты считаются **в Go** (`internal/stats`) по делам, которые пересекают период: SQL отдаёт строки (`instance_details`), чистая функция `Compute` считает. Так границы локальных дней, переход на летнее время и объединение интервалов проверяются обычными юнит-тестами, а объёмы малы (дела одного пользователя за период). Раньше здесь предполагались `range_agg` и рекурсивные CTE в SQL.

- **Период** — `[from, to)`, не больше 366 дней. Перед подсчётом серии периода материализуются (та же функция `Materialize`), чтобы запланированные экземпляры неоткрытых окон тоже попали в план.
- **Дни** — локальные дни пояса пользователя (в день перехода на зимнее время — 25 часов). Интервалы обрезаются по границам периода и по границам дней.
- **Факт дела:** `done`, `partial` и `in_progress` с `actual_start`. Идущий таймер считается до «сейчас», но не больше 12 часов (`MaxTimerDuration`): забытый «Старт» не наполняет статистику; такие таймеры считаются в `long_running_timers`. Неотмеченные дела, `not_done`, `rescheduled` и `cancelled` в факт не входят.
- **По категориям.** Для каждого дела берётся множество DISTINCT «свои категории + все предки» (в том числе архивные), и обрезанная длительность прибавляется к каждой категории этого множества. «Бег» + «Плавание» внутри «Спорта» дают Бег 1 ч, Плавание 1 ч, Спорт 1 ч. Дела без категории — отдельно (`uncategorized_minutes`). Дерево строит клиент по списку категорий.
- **Общее занятое время** (`actual_minutes`, `planned_minutes`, за день) — объединение интервалов: параллельные дела не считаются дважды. Суммы по категориям и по делам — именно суммы, поэтому они могут быть больше занятого времени.
- **По делам** — группировка по названию (допущение 6): число дел и часы.
- **По дням** — занятое время дня и разбивка по «цветной» категории каждого дела (первая по названию, как в календаре), чтобы дело в стопке графика не учитывалось дважды.
- **План против факта.** В план входят дела с `planned_start` в периоде, кроме перенесённых оригиналов (в план входит новое дело). Дело вне плана входит в факт и категории, но не в план; его время показывается отдельно (`unplanned_minutes`). Процент выполненных — `done / (done + partial + not_done + unmarked)`; пока ни одно дело не решено, процента нет. «Опоздания» — дела с отклонением `started_late`, «затянувшиеся» — с `finished_late`.
- **Список отклонений** — дела с отклонением и дела `not_done`/`partial`/`rescheduled` с комментарием, по плановому началу.
- **Неотмеченные** (FR-8.7) — в факт не входят, показывается их число.

**Экран.** День / неделя / месяц / произвольный период (≤ 366 дней) со стрелками. Крупно — факт; плитки: процент выполненных, опоздания, затянулось, не выполнено, перенесено, не отмечено. График «часы по дням» — столбики-стопка по категориям; для периода длиннее 62 дней столбики — недели. На графике до 8 рядов: 7 крупнейших категорий со своим цветом и нейтральный ряд «Другое». Цвет следует за категорией, а не за её местом в рейтинге. Дела без категории — нейтральный ряд «Без категории». Для однодневного периода графика нет. Кроме цвета категории различают легенда, подсказка при наведении/фокусе и таблица-двойник («Таблица»).

### Напоминания

1. **Планировщик** (`reminder.Service.PlanAll`) запускается раз в минуту. Для каждого пользователя с включённым общим выключателем он:
   - материализует серии в окне, расширенном на наибольшее смещение правил пользователя;
   - берёт запланированные и идущие дела, план которых заходит в это окно, и для каждого находит действующие правила (`Resolve`);
   - для каждого правила вычисляет время срабатывания (`FireAt`) и кладёт строку в `notifications`, если оно не раньше чем 30 минут назад и не позже чем через 5 минут, а дело ещё в подходящем состоянии (`Needed`); дубликаты отсекает `dedupe_key`;
   - для привычек вне сетки — по правилам `habit_time` в дни, когда привычка запланирована (для «N раз в неделю» — в любой день).
2. **Тихие часы.** `send_at` внутри тихих часов сдвигается на их конец (`Quiet.Shift`).
3. **Правка настроек** удаляет все неотправленные строки пользователя: планировщик на следующем проходе создаёт нужные заново. Отправленные остаются, и их ключ не даёт отправить напоминание второй раз.
4. **Отправитель** (`SendDue`, каждые 10 секунд) берёт строки со `send_at` в прошлом, **заново проверяет состояние** дела или привычки (отмечено — строка снимается), находит Telegram-аккаунт пользователя и отправляет. Ошибка — повтор с паузами 30 секунд, 2, 10, 30 минут, всего 5 попыток; «бот заблокирован» и «чат не найден» — без повторов.
5. **Кнопки** сообщений несут `действие:uuid` (до 64 байт). Бот находит пользователя по Telegram-id нажавшего, проверяет, что дело в подходящем состоянии, и вызывает те же методы, что и экран. «Открыть» — кнопка `web_app` на `WEBAPP_URL`.
6. **Бот** — пакет `reminder` (`Bot`), на `go-telegram/bot` с long polling; запускается при `BOT_ENABLED=true`. Всё, что он решает, лежит в `Service`, у бота — только отправка, `/start` и разбор нажатий.
7. **Разрешение на сообщения.** При включении напоминаний Mini App вызывает `Telegram.WebApp.requestWriteAccess()`.
8. Напоминания исходного дела при переносе удаляются вместе с делом; у нового дела свои, по тем же уровням.

### Привычки

- Отметки хранятся по **локальной дате** пользователя.
- Расписание, серии, лучшая серия, процент и тепловая карта считаются чистыми функциями пакета `habit` по списку отметок, дате создания и «сегодня» пользователя (правила — допущение 8 в `docs/requirements.md`).
- Привычка в сетке: когда экземпляр её серии **становится** `done` (переход, а не повторная правка выполненного), в той же транзакции (в `task`, в функции установки статуса) за локальную дату плана создаётся или повышается запись в `habit_logs` до цели; меньшее значение, поставленное вручную, запоминается в `base_value`. Когда экземпляр перестаёт быть `done` (в том числе после ухода привычки из сетки), засчитанное им удаляется, а прежнее ручное значение возвращается. Ручная правка значения обнуляет `task_instance_id`.
- Привычки не пересекаются со статистикой времени сами: время в факт даёт экземпляр из сетки как обычное дело.

Веб-версия — ещё одна реализация этого интерфейса.

**Загрузка `telegram-web-app.js`.** Скрипт не подключается в `index.html`: синхронный скрипт с telegram.org держал бы пустую страницу там, где telegram.org заблокирован. Его грузит `loadTelegramWebApp` и только внутри Telegram, с таймаутом 10 секунд. Признак запуска в Telegram — `tgWebAppData` в хэше адреса, а после перезагрузки внутри Telegram — в `sessionStorage` (`__telegram__initParams`, туда его кладёт сам скрипт). В браузере скрипт не грузится. До старта React в `#root` стоит текст «Загрузка…».

**Что используется из Telegram WebApp:**

- `ready()`, `expand()`;
- `disableVerticalSwipes()` — иначе протягивание по сетке закрывает приложение;
- `themeParams` → CSS-переменные;
- BackButton;
- HapticFeedback;
- safe area;
- `requestWriteAccess()`;
- `start_param` — для приглашений, после MVP.

**Сетка календаря** — свой компонент:

- Линии слотов — CSS-фон (`repeating-linear-gradient`), а не DOM-элемент на каждый слот: неделя со слотами по 5 минут — это 2016 слотов.
- Дела — абсолютно позиционированные блоки.
- Точка касания переводится в минуты с привязкой к слоту: `floor(y / pxPerMinute / slot) * slot`.
- Параллельные дела раскладываются классическим алгоритмом: сортировка по началу, группы пересекающихся дел, жадное назначение колонок. Это чистая функция с тестами.
- Выделение: на тач-устройствах — долгое нажатие и протягивание, мышью — зажать и тянуть.

## Тестирование

- **Unit-тесты Go:**
  - разворачивание повторов, включая переходы на летнее время и все три области правки;
  - проверка `initData` на эталонных данных;
  - отклонения;
  - серии привычек;
  - определение действующих правил напоминаний: все уровни, наследование в дереве категорий, объединение правил;
  - тихие часы.
- **Интеграционные тесты Go** на настоящем PostgreSQL:
  - статистика, включая свёртку по дереву категорий и объединение интервалов;
  - материализация;
  - перенос;
  - планировщик напоминаний.
- **Vitest:**
  - раскладка параллельных дел;
  - расчёт слотов;
  - преобразование «форма повтора ↔ RRULE».
- **E2E (Playwright)** — в настоящем Chromium через `DEV_AUTH`, на изолированном стенде (`make e2e`):
  - жесты выделения слотов мышью и касанием (долгое нажатие и протяжка, быстрый свайп только прокручивает);
  - геометрия блоков: наложение, дела через полночь;
  - создание, правка и удаление через формы, цвет по категории, навигация и выбор даты;
  - тёмная тема;
  - нагрузка: недельный вид, слоты по 5 минут, 300 дел (NFR-4).

## Окружение разработки

- **Go:** системный Go 1.23.4 лежит в `/usr/local/go/bin`, но в неинтерактивном shell его нет в PATH. В `go.mod` указан Go 1.27, нужный toolchain скачается автоматически (`GOTOOLCHAIN=auto`).
- **БД:** Postgres в Docker на `127.0.0.1:5433`, потому что порт 5432 занят проектом `diary`.
- **Тесты с БД:** используют dev-Postgres, каждому тесту выдаётся отдельная схема (`TEST_DATABASE_URL`, см. `CLAUDE.md`).
- **Фронтенд:** dev-сервер Vite с прокси `/api` на бэкенд. Вне Telegram работает адаптер `browser` и вход через `DEV_AUTH`.
- **Проверка внутри настоящего Telegram** возможна только после деплоя: Mini App нужен публичный HTTPS-адрес.

## Деплой

Файлы — в `deploy/`: `docker-compose.yml`, `web.Dockerfile`, `Caddyfile`, `.env.example`; образ бэкенда — `backend/Dockerfile`. Сборка идёт из корня репозитория. Секреты лежат только в `deploy/.env`, который не коммитится. Запуск: `make deploy`.

- Адрес Mini App — `https://plan.72-56-242-50.sslip.io` (бесплатное имя: sslip.io отдаёт на IP сервера любой поддомен; сертификат Let's Encrypt выдан на него, Caddy продлевает его сам). Сменить имя: поправить `DOMAIN` в `deploy/.env`, выполнить `make deploy` и обновить кнопку меню бота (`setChatMenuButton`).
- Вход общий с проектом `diary`, который живёт на этом же сервере: 80 и 443 может слушать только один процесс, поэтому наш Caddy обслуживает оба имени. Голое имя `72-56-242-50.sslip.io` отдаёт `diary` (`deploy/sites/diary.caddy`: прокси на его бот, `127.0.0.1:8080`), `plan.…` — scheduler. Файлы `deploy/sites/*.caddy` подключаются в Caddyfile. У проектов разные имена, базы (`5432` у diary, `5434` у нас), внутренние порты (`8080` и `8081`), боты и тома. Делить одно имя по путям нельзя: у обоих есть `/api`. Собственный Caddy из compose-файла `diary` (профиль `web`) запускать не нужно. Минус общего входа: пока Caddy перезапускается (`make deploy`), оба сайта недоступны на пару секунд.
- Сервисы `docker compose` (проект `scheduler`):
  - `db` — Postgres 18, том `db-data`; опубликован только на `127.0.0.1:5434`;
  - `backend` — статический бинарник под непривилегированным пользователем; `APP_ENV=prod`, `DEV_AUTH` выключен; слушает `127.0.0.1:8081`; миграции применяются при старте; `BOT_ENABLED=true`, поэтому бот и напоминания работают в том же процессе;
  - `web` — Caddy со статикой Mini App (`/srv`) и прокси `/api/*` на `127.0.0.1:8081`; единственный публичный вход (80 и 443).
- `backend` и `web` работают в сети хоста (`network_mode: host`). С этого сервера Telegram API по IPv4 недоступен, а по IPv6 доступен; у bridge-сетей Docker здесь нет IPv6, и бот внутри такой сети получал бы таймауты. Наружу при этом смотрят только порты 80 и 443.
- Файлы с хэшем в имени (`/assets/*`) кэшируются навсегда, страница — `no-cache`.
- `diary-caddy-1` остановлен командой `docker stop` по просьбе пользователя (политика `unless-stopped` не поднимет его после перезагрузки) и больше не нужен. Бот и база `diary` запущены его же `docker compose up -d db bot` из `/home/dev/dev/diary`.
- Резервные копии БД не делаем (решение пользователя).
- Бот `@chel_scheduler_bot`: токен — `BOT_TOKEN` в `deploy/.env`. Через Bot API заданы кнопка меню «Планировщик» (Mini App), команда `/start` и описания.
